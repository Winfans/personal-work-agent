# 0005 — MySQL 会话与消息持久化

- 状态：已采纳；缺少真实 MySQL 运行验证
- 日期：2026-10-17

## 背景

原聊天界面只在 React 内存保留当前对话，重启后无法恢复，也不能切换多个会话。现有服务已经通过 SQLAlchemy 使用 MySQL 存笔记。用户要求多会话聊天历史及对应 UI。

## 决策

以 `conversations` 存会话摘要，以 `conversation_messages` 逐条存完整的用户和助手消息。列表只查会话摘要，消息按 ID 倒序取一页后以时间正序交给 UI；UI 初次展示最近 50 条，继续向前分页。完整历史保存在 MySQL，不因为 Agent 上下文窗口而裁剪。Agent 每次取最近至多 100 条作为上下文。

新增 `/api/v1/conversations` JSON 接口，遵守统一响应结构。`POST /api/v1/conversations/{id}/run` 复用原 Agent 服务，先保存用户消息，流式产生回答，并在 `done` 前保存完整助手回答。流失败时保留用户消息，不保存未完成助手消息。原 `/agent/run` 与 `/chat/text` 接口继续兼容，且不隐式持久化。

## 取舍

复用 MySQL，避免引入第二个数据源。Redis 可作为未来经测量后的热点缓存，但不是历史记录权威来源。由于目前没有迁移框架，新表由启动阶段 `create_all` 创建；后续 schema 变更需引入迁移机制。当前没有用户身份和权限隔离，只适用于单用户本地工作台，不能直接暴露为多用户服务。

## 验证

后端 API 使用虚拟服务和虚拟 Agent 测试，不依赖真实数据库或模型。真实 MySQL 的建表、写入、重启恢复需要单独运行验证。
